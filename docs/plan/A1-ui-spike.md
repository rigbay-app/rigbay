# Task A1: WinUI 3 spike (elevated, modules, logon task)

Track A1: spike that settles the UI framework. Target is WinUI 3; prove it works or report a hard blocker with evidence.

## Goal
Rigbay's host is an elevated (administrator) desktop app that loads module DLLs in-process and shows a modern Fluent UI (Windows App SDK / WinUI 3, Mica). The spike must PROVE, by running it, three things:
- (a) An **unpackaged, elevated** WinUI 3 window runs reliably on this machine (Windows 11 10.0.26300): starts, shows a window with Mica backdrop and a custom/extended title bar, stays responsive, exits cleanly. Try both framework-dependent (using the Windows App Runtime packages already installed here: 1.6, 1.8 and 2.x; check with `Get-AppxPackage *WindowsAppRuntime*`) and self-contained; report size, start-up time and which one works without installing a runtime.
- (b) A **module DLL loaded at run time** (from a folder, via `AssemblyLoadContext` or similar) can **contribute a page** to the host's navigation. Define a tiny `Rigbay.Abstractions` interface (module id/name, version, `Probe()` result, `CreatePage()` returning something the host can show) and a sample module in a separate project. The hard part is the UI: compare, by trying, (1) the module returning a WinUI `UIElement` built in C# code, (2) a module with its own XAML pages (XAML compiled into the module, resource lookup through `ms-appx:`/`Application.LoadComponent` in an unpackaged app with a dynamically loaded assembly), (3) anything else you find viable. Report which of them actually work, which fail and the exact error, and which you recommend. Also check that the host and the module share the same WinUI/Windows App SDK types (no duplicate copies, no type identity problems) and that an exception thrown inside a module call can be caught at the host boundary without crashing.
- (c) The app **starts at logon through a scheduled task with highest privileges**. Create a scheduled task named `RigbaySpike` (logon trigger, run level highest, your spike exe), start it with `schtasks /run /tn RigbaySpike`, and verify the process is elevated and its window exists. A real logoff/logon cannot be done by you: say so under "not verified". Delete the task when finished.
Quick extra probes (a line each in the report, do not polish): tray icon from an elevated WinUI 3 app (WinUI has none built in: P/Invoke `Shell_NotifyIcon` or a library), global hotkey with `RegisterHotKey` on the window's HWND, toast notification from an unpackaged elevated app, single instance, dark/light theme following Windows, DPI 100%/150% rendering if you can, language switching at run time through simple key=text language files (the format used by xtu-profile-switcher: `@code`/`@name` header, `key = text`).

## Toolchain (important)
This machine has the .NET 8 runtimes (Microsoft.NETCore.App 8.0.24, WindowsDesktop 8.0.24) but **NO .NET SDK and no Visual Studio**. You need an SDK to build. The coordinator has asked the user to approve installing one (a gate on your task). **Do not install anything yourself.** Wait: your task starts blocked until the user answers; the answer (which SDK, or "reject") will be in the task result / mail from the coordinator. If you were started and the SDK is still missing (`dotnet --list-sdks` prints nothing), mail the coordinator and stop with `RESULT: blocked`.
Once an SDK exists: write the projects by hand as SDK-style `.csproj` (the Visual Studio templates are not available): `Microsoft.WindowsAppSDK` NuGet package, `<UseWinUI>true</UseWinUI>`, `<WindowsPackageType>None</WindowsPackageType>`, `<WindowsAppSDKSelfContained>` as needed, `TargetFramework` like `net10.0-windows10.0.19041.0` (or what the approved SDK supports), `app.manifest` with `requireAdministrator` for the elevated variant. NuGet restore from nuget.org into the user's package cache is allowed; no other system change. Keep package versions pinned and record them.

## Visual quality
Load the `impeccable` and `design-taste-frontend` skills BEFORE you design the spike's shell window. Apply their principles to a native app: flat surfaces and hairlines, colour carries data, honest empty/error states, text at least 4.5:1 contrast in light and dark, no decorative cards/pills/gradients/glow, short copy, one product-specific element (for example a "bay" slot motif for modules). The shell needs: a NavigationView-like left list of modules (the sample module appears there), a page area, a status line with the host/Abstractions/Windows App SDK versions, and honest empty and error states (a module that fails to load is shown as failed with the reason). Keep it small; this is a spike, not the product. Check the result visually: render the window itself to a PNG (PrintWindow or `RenderTargetBitmap`, from inside the app or from a helper) and LOOK at it with the Read tool; save the final PNGs in `docs/spike/`. Never capture the user's real screen.
