# Task A2: Abstractions v0.1 and the host core (no UI framework code)

## Goal
Contract first. Write the small versioned `Rigbay.Abstractions` assembly that modules reference, and `Rigbay.Core`, the UI-independent host logic that loads and supervises modules. The WinUI shell (task A3) and every module are written against what you produce, so the contract must be right, small and documented. Read `README.md`, `docs/DESIGN.md`, `docs/UI-DIRECTION.md` (section 5 explains the two-level page model) and `docs/plan/WORKER-RULES.md` first.

## Decisions already made (do not reopen; flag problems by mail)
- Modules are DLLs loaded in-process into an elevated host, from an admin-only folder, one `AssemblyLoadContext` per module; `Rigbay.Abstractions` is shared from the default context (type identity!). Every call into a module goes through a fault boundary: an exception disables that module, logs it, and never takes the host down.
- `Rigbay.Abstractions` has NO UI-framework types and no Windows App SDK reference. Target `net8.0` (so a module can also target net8.0 or later). `Rigbay.Core` targets `net10.0` (the installed SDK is 10.0.403; there are .NET 8 and 10 runtimes). Use SDK-style projects, nullable enabled, `Directory.Build.props` at the repo root, a `Rigbay.sln` (or `.slnx`). `Rigbay.Abstractions` is packable as the NuGet package `Rigbay.Abstractions` (do not publish).
- Module manifest `module.json` next to the module DLL: id (lowercase, `[a-z0-9-]`), name, version (semver), author, description, entry assembly and type, `hostApi` supported range, `group` (one of a fixed list: power, cooling, network, display, monitoring, other), `requires` (informational: admin, network ports, registry, services), optional `languages` folder. The host reads it BEFORE loading any code.
- Contract pieces, all in Abstractions: `IModule` (lifecycle: `Probe()` returning supported/unsupported + a human reason key, `Initialize(IHostServices)`, `Shutdown()`), `IHostServices` (settings, localisation, log, hotkeys, tray items, commands, toast, metrics bus), the **declarative page model** (Page > Groups > Rows; row kinds: toggle, choice, number, text, shortcut, button, read-only value, live reading, expander, info bar; each row has header/description localisation keys, an observable value, enabled state; a button/toggle that changes hardware state is marked `ChangesHardware` with an effect description key so the host can confirm and offer revert) plus a **custom page escape hatch** (`object`-typed handle created by a provider interface, leaving the host framework out of the contract; A1/A3 decide the concrete control type later), the **metrics bus** (`MetricId`, unit, value, timestamp, source module; publish and subscribe, with the latest value cached), and the **API version** constant with a range check.
- Language files: same format as xtu-profile-switcher (`D:\Documents\Projects\driver-setup\xtu-switcher`, files `Loc.cs` and `lang\*.lang`, plus its skill under `.claude/skills/xtu-switcher/`): `@code`/`@name` header, `key = text`, English reference, fallback current language > English > key. Module keys are prefixed `module.<id>.`. Provide a `--langcheck` capability in Core (missing keys, unused keys, placeholder mismatch) as a library function plus a small console tool.
- Settings: per-module JSON file under `%LOCALAPPDATA%\Rigbay\modules\<id>\settings.json`, atomic write, version field, defaults, corrupt file -> backup and defaults + log, never a crash.
- Commands: `rigbay <module> <verb> [args]` registry in Core (parse + dispatch + exit codes: 0 ok, 1 failed, 2 not found or bad usage; output text). Hotkeys: registry with conflict detection across modules (data only; the OS registration belongs to the UI host). Tray items: registry (data only). Toast: interface only.
